把 Agent 能力产品化成飞书里的团队协作入口：群内自然语言 → 确定性工作流路由 → 受控工具执行（飞书 CLI ／ 电商 MCP）→ 结果回到飞书；配置、上下文与授权全部落库，链路可按阶段编号完整回放。

二、按分层看每个类的职责

1. 接入层（Controller）
FeishuEventController

飞书事件唯一入口：URL 验证、解析、message_id 去重、把任务投递给线程池。

设计要点：回调线程只做「快速 ACK」，不在 Tomcat 线程里跑 Agent，避免飞书重推与线程被慢任务占满。

FeishuOAuthController

用户身份授权回调：接收 code / state，换取 token 并落库。

设计要点：state 由服务端生成与校验，token 由服务端统一保存与刷新。

WorkflowAdminController

POST /api/admin/workflows/import 导入 YAML / JSON 工作流定义。

设计要点：新增一条业务线 = 导入一份配置，不改代码、不重新编译。

HealthController

/api/health 健康检查。

设计要点：部署脚本以该接口为准判定发布成功，「容器在跑」不算发布成功。

2. 解析与去重层
FeishuEventParserService

飞书原始 JSON → 内部 FeishuMessageEvent（sender / message / content / mentions）。

设计要点：外部协议只在这一层解析，业务层统一拿到领域对象。

MessageDedupService

按 message_id 去重，记录保留 30 分钟。

设计要点：挡的是平台重试同一事件；用户手动重发（新 message_id）不拦。

3. 业务入口与编排层
AdminAgentService

后台处理一条消息：帮助指令、处理中表情、授权二维码，再进入 Agent 流程。

设计要点：业务入口只做「简单回复 or 走 Agent」的分流，不掺工具逻辑。

AgentOrchestratorService

先跑工作流路由；未命中才进入 Agent 多步循环（读记忆 → 规划 → 执行工具 → observation → 再规划），最大 10 步。

设计要点：工具已返回终态回复时本轮直接结束，不被模型的二次解释覆盖。

FeishuOpenApiService

飞书 OpenAPI 封装：回复文本、图片、reaction、卡片。

设计要点：业务层不直接拼 HTTP 请求，统一日志与错误处理。

QrCodeService / LlmErrorUtils

授权链接转二维码；把「大模型余额不足」等底层错误翻成中文提示。

设计要点：用户只看到可执行的下一步，不看到堆栈与原始异常。

4. 工作流路由与执行层
WorkflowRouterService

两段式路由：① 规则召回——读取 workflow_definition 全表，名称／编码命中 +60 分，每个关键词 +16/+24 分，双关键词再 +20 分，低于 20 分不进候选，最多 5 个候选；② 大模型只在候选内裁决，置信度低于 0.85 则放弃。

设计要点：Java 收口——模型返回候选外的 workflowCode 直接拒绝；customerName / months 等参数从用户原文归一化补齐。宁可不命中，也不错执行。

WorkflowExecutionService

按 stepNo 顺序执行，模板 {{key|default:值}} 渲染，onError: STOP 控制失败策略。

设计要点：四种执行器各司其职：MCP（取结构化数据）／CLI（飞书能力）／LLM_SUMMARY（只做中文总结）／FEISHU_REPLY（产出最终回复）。遇到未实现的执行器直接失败，不静默成功。

WorkflowImportService

YAML / JSON → 校验 → 写入 workflow_definition + workflow_step，原始内容保留在 source_content。

设计要点：配置即代码，导入原文可回放、可对比、可排错。

WorkflowDefinition / Step / RouteResult

工作流的数据对象：定义、步骤、候选与路由结果。

设计要点：路由结果携带分数与命中原因，日志可解释「为什么命中这一条」。

5. Agent 规划层
AgentPlannerService

每轮拼装提示词：工具清单 + 业务 Skill + 当前群 chatId + 会话记忆 + 今天／明天日期，模型必须输出 JSON（tool_call 或 final_answer）。

设计要点：路由规则写进提示词：像常用业务流程先 workflow.list；电商数据走 MCP；飞书内部操作走 cli.run_skill；不得编造 ID、不主动索要授权。

AgentDecision / ToolCall / ToolResult

决策、调用、观察结果三个数据对象。

设计要点：observation 回灌下一轮，形成「规划—执行—观察」闭环。

6. 工具层与安全
ToolRegistryService

模型只能调用白名单内的 6 个工具：cli.run_skill、feishu.scope_for_domain、ecommerce.list_tools、ecommerce.call_tool、workflow.list、workflow.run；统一 90s 超时、独立 8 线程池、结果标准化。

设计要点：未知工具直接返回失败，模型不能自己发明能力。

ToolPermissionService

按 open_id / chat_id 白名单放行工具调用。

设计要点：权限判断落在 Java 代码里，不依赖提示词约束。

DestructiveCommandGuard

执行前拦截高风险 CLI：--yes、+delete / +remove / +revoke / +clear 类子命令；--help 放行。

设计要点：确认必须来自用户当前消息的原话，不能用模型改写过的目标描述当作同意。

SkillCliExecutorService

内层 CLI 循环：先 lark-cli skills read 取原生说明书，再叠加项目补充规则 skills/lark/<domain>.md；上限 15 步、单条命令 60s；身份默认机器人，用户明确要求才切换用户身份。

设计要点：同一条命令重复失败要立即停止并回报真实原因，而不是重试到超时。

7. 记忆与授权落库层
ConversationMemoryService

按 memory_key = chat_id 保存 user / assistant 原文；超过 20 条压缩为摘要，保留最近 8 条，摘要上限 4000 字。

设计要点：同一群共享团队上下文，不同群与私聊天然隔离。

UserOAuthTokenService

OAuth state 生成与校验、token 保存与刷新、scope 合并。

设计要点：复合任务（云文档 + 文档、多维表格 + 云盘）预先合并 scope，避免用户反复扫码。

FeishuUserScopeMappingService

业务域 → 所需 scope 集合的映射表。

设计要点：「要授权哪些权限」是配置，不让模型临场猜。

OAuthPermissionReplyFormatter

把授权请求写成用户看得懂的内容：业务域、scope 数量、缺失项。

设计要点：授权消息必须说明在申请什么权限，而不是只发一句「请扫码」。

三、Skill 分层：执行知识与业务规则分离

层位置回答什么问题谁读取
飞书原生 Skilllark-cli skills read lark-*（15 个业务域）飞书 CLI 原生能力是什么、命令与参数怎么用SkillCliExecutorService
项目补充规则skills/lark/<domain>.md本项目的额外约束：默认身份、群内回复引用、业务域边界SkillCliExecutorService
业务能力 Skillskills/business/*.md这类需求该走哪条工具链、明确不该做什么AgentPlannerService
Java 安全层ToolRegistry / ToolPermission / DestructiveCommandGuard这个人有没有权限、能不能安全执行代码，而非提示词
边界公式：原生 Skill 回答「怎么执行」，业务 Skill 回答「走哪条路」，Java 回答「该不该授权、能不能安全执行」。

电商逻辑不在机器人进程内：机器人只负责「调工具」，电商服务自己负责「怎么查」。两侧的契约就是工具名 + 入参 + 结构化返回。

五、MCP 工具契约（5 个工具）

工具名（ecommerce. 前缀）入参 · 用途
query_top_productslimit（默认 5）· 销售额最高商品排行
query_low_inventorythreshold（默认 50）· 低库存与补货预警
query_customer_orderscustomerName、months（默认 12）· 客户订单与消费偏好
query_refund_top_productslimit（默认 5）· 退款与售后分析
query_activity_reportactivityName · 活动复盘与经营汇总
工具名统一 ecommerce. 前缀，用途与参数写进工具定义——模型看到的是工具说明书，而不是数据库表结构；未知工具名直接返回失败。

数据表：ecommerce_product_sales（商品销售）、ecommerce_customer_orders（客户订单明细）、ecommerce_refund_stats（退款统计）；服务启动时按 schema-mysql.sql + data-mysql.sql 初始化数据集，保证结果可复现。

六、两条到达 MCP 的路径

路径一：工作流步骤 executorType=MCP

由数据库配置决定调哪个工具。

确定性：步骤、参数、顺序固定，可复现、可审计，耗时十几秒量级。

路径二：Agent 循环 ecommerce.call_tool

由大模型在多轮规划中选择工具。

灵活性：可处理未配置过的问法，需要多轮规划，耗时几十秒量级。

两条路径都经过同一个 Java 工具层：白名单、权限校验、90s 超时、独立线程池。差别只在「谁决定调哪个工具」。

八、一次真实电商请求的完整链路

用户（群内）：查一下张伟最近 12 个月的订单，整理成卡片发到本群

1. FeishuEventController：验证请求、message_id 去重、立刻返回 200，任务进入线程池。
2. AgentOrchestratorService：先回复「⏳ 正在处理」并添加表情，让用户知道任务在跑。
3. WorkflowRouterService：读取启用工作流，关键词命中「订单」，大模型裁决置信度达标 → 命中 ecommerce_order_summary，参数归一化为 customerName=张伟, months=12。
4. 步骤 1（MCP）：调用 ecommerce.query_customer_orders，返回真实数据：7 笔订单、合计 3041 元、品类分布美妆 2 ／ 数码 3 ／ 服饰 2。
5. 步骤 2（LLM_SUMMARY）：只基于第 4 步的数据生成中文结论，不接触数据库。
6. 步骤 3（FEISHU_REPLY）：生成卡片内容作为 finalReply，由外层统一回复到群。
7. ConversationMemoryService：本轮问答落库，下一句可以直接接着聊。

对照场景：换成「查一下库存低于 20 件的商品，哪些是畅销但库存不足」——工作流库中没有对应流程，路由不命中，走 Agent 循环 + MCP：得到 4K 运动相机（库存 5 ／ 销量 18）、宠物自动喂食器（库存 6 ／ 销量 38）、人体工学椅（库存 7 ／ 销量 21）、智能手表（库存 9 ／ 销量 33）。

三个可核对的数字：命中工作流约十几秒、Agent 路径几十秒、回复里的每个数字都能在 MCP 返回中逐项对上。

九、健壮性设计（边界与失败处理）

风险处理方式位置
飞书重复推送同一事件按 message_id 去重，保留 30 分钟MessageDedupService
模型无限调用工具Agent 循环上限 10 步；CLI 循环上限 15 步，超限给出保护性回复AgentOrchestratorService / SkillCliExecutorService
工具卡住拖死线程统一 90s 工具超时、60s 单条 CLI 超时，独立 8 线程池与有界队列ToolRegistryService
越权调用工具open_id / chat_id 白名单，不符合直接拒绝并说明原因ToolPermissionService
破坏性操作被误执行执行前拦截 --yes 与删除类子命令，要求用户原话确认DestructiveCommandGuard
模型选错工作流只能在规则召回的候选内裁决，置信度阈值 0.85，Java 校验 workflowCodeWorkflowRouterService
MCP 返回未知工具或失败服务端返回失败结构，调用方按步骤 onError 处理，不写入编造数据MCP 服务 / WorkflowExecutionService
用户权限不足按业务域预合并 scope 生成一次授权，缺权限时说明缺少什么UserOAuthTokenService
大模型余额不足或异常识别为可读错误并回复中文提示，不把底层异常抛给用户LlmErrorUtils

十一、关键设计权衡

选择收益代价与应对
高频业务做成数据库里可配置的工作流，而不是全部交给模型结果可复现、步骤可审计、耗时稳定需要维护配置与步骤定义；用 source_content 保留导入原文，支持回放与排错
电商能力抽成独立 MCP 服务能力可被其他 Agent / 工具复用，机器人与电商系统解耦多一个服务与一条网络链路；用连接与读取超时、失败结构约束影响面
权限、超时、破坏性确认全部放在 Java 层安全判定确定，不受提示词质量影响新增能力需同步维护白名单与规则，换来的是不可绕过的边界
飞书 CLI 能力走原生 Skill + 项目补充规则，而非手工复制命令手册CLI 升级不牵连业务代码，模型拿到的是最新说明书补充规则要克制，只写项目特有约束，避免两层互相矛盾
记忆按 chat_id 维度保存并压缩团队共享上下文，跨群隔离，上下文长度可控同群内多用户共享上下文，属于产品预期，需在文档中说明

一句话总结：飞书回调只做快速应答，编排层负责把慢任务与并发管住，路由层用「规则 + 大模型裁决 + Java 校验」把高频业务变成确定性执行，未命中的长尾交给模型在白名单工具内规划；所有真实动作都由受控工具完成——飞书侧走 lark-cli 与原生 Skill，电商侧走独立 MCP 服务；上下文、配置与授权全部落库，链路可按阶段编号日志与导入原文完整回放。

部署形态：Docker Compose 双环境（演示环境与线上环境各自独立容器与独立数据库，共享同一 MCP 服务与 MySQL 实例）；外部依赖：飞书开放平台事件回调与 OpenAPI、自研电商 MCP 服务、大模型服务。
