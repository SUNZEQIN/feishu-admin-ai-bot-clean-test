# 工作流的命中规则

## 1. 目标

工作流命中采用“三层保护”：

1. Java 从数据库读取启用的工作流并进行规则召回。
2. 大模型只能在 Java 召回的候选工作流中进行语义裁决。
3. Java 最后校验 workflowCode 和置信度，确认后才执行 workflow.run。

这样可以减少大模型自由编造工作流或误执行业务流程。

## 2. 数据来源

工作流定义表：workflow_definition

Java 查询条件：

    SELECT workflow_code, workflow_name, domain, risk_level,
           require_user_confirm, intent_keywords, description
    FROM workflow_definition
    WHERE enabled = 1
    ORDER BY updated_at DESC

| 字段 | 用途 |
| --- | --- |
| workflow_code | 工作流唯一编码，也用于校验大模型返回值 |
| workflow_name | 工作流名称，支持完整名称命中 |
| domain | 工作流业务域，例如 ecommerce |
| intent_keywords | 用户意图关键词列表 |
| description | 工作流能力描述，用于弱匹配和大模型理解 |
| enabled | 是否参与路由 |
| risk_level | 执行风险等级 |
| require_user_confirm | 执行前是否要求用户确认 |

## 3. Java 规则打分

Java 会把用户原文转换为路由文本，然后逐个工作流计算分数。

| 命中条件 | 分值 |
| --- | ---: |
| 完整命中 workflow_name | +60 |
| 完整命中 workflow_code | +60 |
| 命中长度大于等于 4 的关键词 | +24/个 |
| 命中长度小于 4 的关键词 | +16/个 |
| 至少命中 2 个关键词 | +20 |
| description 长文本弱匹配 | +10 |

最低召回分数：

    MIN_RULE_SCORE = 20

低于 20 分的工作流不会进入候选列表。

最多交给大模型裁决的候选数量：

    MAX_CANDIDATE_SIZE = 5

候选按规则分数从高到低排序，只保留前 5 个。

## 4. 示例

假设数据库中有：

    workflow_code: ecommerce_order_summary
    workflow_name: 电商订单消费总结
    intent_keywords: 查订单、消费总结、买了什么、客户订单
    description: 查询客户订单，汇总消费金额、品类偏好，并生成飞书回复

### 4.1 命中工作流名称

用户输入：

    帮我执行电商订单消费总结

命中 workflow_name：

    规则分数 = 60

进入候选列表。

### 4.2 命中一个关键词

用户输入：

    帮我查一下客户订单

命中关键词 客户订单：

    规则分数 = 24

进入候选列表。

### 4.3 命中多个关键词

用户输入：

    查询客户订单，并做消费总结

命中：

    客户订单       +24
    消费总结       +24
    多关键词组合   +20
    总分           68

这是较明确的候选。

### 4.4 不匹配

用户输入：

    查询最近10天销售额最高的商品，并分析库存不足风险

如果当前工作流只有：

    查订单、消费总结、买了什么、客户订单

则可能得到：

    规则分数 = 0
    候选数量 = 0

Java 不会命中该工作流，应继续使用电商 MCP 或飞书 CLI。

## 5. 大模型裁决

只有 Java 规则分数达到 20 分的工作流才会进入大模型候选列表。

大模型必须返回：

    {
      "matched": true,
      "workflowCode": "候选工作流编码",
      "confidence": 0.9,
      "reason": "用户目标与工作流能力匹配",
      "arguments": {}
    }

Java 会继续校验：

1. workflowCode 必须属于 Java 召回的候选列表。
2. confidence 必须大于等于 0.85。
3. matched 必须为 true。
4. 用户目标和工作流描述必须真正匹配。

任一条件不满足，都视为未命中。

## 6. Java 最终安全校验

大模型只负责提出“是否命中以及可能的工作流”，不能直接执行工作流。
Java 收到大模型结果后，按以下顺序进行最终校验。

### 6.1 校验 matched

大模型必须返回：

    "matched": true

如果返回 false，或者字段缺失，Java 直接判定未命中，不执行 workflow.run。

### 6.2 校验 workflowCode

Java 会在本次规则召回的候选列表中查找大模型返回的 workflowCode。

例如本次候选只有：

    ecommerce_order_summary

大模型返回该编码时才允许继续：

    "workflowCode": "ecommerce_order_summary"

如果大模型返回候选列表之外的编码，即使 confidence 很高也会被拒绝：

    "workflowCode": "delete_all_orders"

拒绝原因：

    LLM 返回了候选外工作流

这样可以防止大模型编造数据库中不存在的工作流，或者绕过 Java 规则直接执行其他工作流。

### 6.3 校验 confidence

当前自动执行的最低置信度是：

    MIN_LLM_CONFIDENCE = 0.85

示例：

    confidence = 0.92
    允许继续

    confidence = 0.72
    放弃工作流，继续外层 Agent

即使 workflowCode 合法，只要置信度低于 0.85，也不会执行。

### 6.4 校验通过后的边界

只有以下条件全部满足时，Java 才会组装参数并调用 workflow.run：

    matched = true
    workflowCode 属于 Java 召回的候选列表
    confidence >= 0.85

调用关系：

    大模型返回裁决结果
            ↓
    WorkflowRouterService Java 校验
            ↓
    AgentOrchestratorService 组装 workflowCode 和 arguments
            ↓
    ToolRegistryService 执行 workflow.run
            ↓
    WorkflowExecutionService 按 workflow_step 顺序执行

workflow.run 的调用不是大模型直接发起的，而是 Java 校验通过后由 AgentOrchestratorService 发起。

### 6.5 特殊情况：LLM 未启用

如果工作流路由大模型未启用，Java 只有在以下条件同时满足时才允许直接命中：

    候选数量为 1，或者第一名与第二名分数至少相差 20 分
    第一名规则分数 >= 60

否则放弃工作流，避免仅依靠低分关键词误执行。

## 7. 命中后的执行流程

    Java 查询 workflow_definition
            ↓
    Java 规则打分
            ↓
    分数 < 20
            ↓
    未命中，进入外层 Agent

    分数 >= 20
            ↓
    生成候选工作流
            ↓
    大模型在候选中裁决
            ↓
    Java 校验 workflowCode 和 confidence
            ↓
    命中后调用 workflow.run
            ↓
    WorkflowExecutionService 按 workflow_step 顺序执行

命中工作流后，外层 Agent 不会再次调用 workflow.list。

## 8. Java 未命中后的行为

Java 已完成规则预检查且没有候选时，会把状态传递给外层 Agent：

    Java 已完成工作流规则预检查，但没有召回候选工作流；
    本轮禁止调用 workflow.list。

除了提示词约束外，AgentOrchestratorService 还会进行 Java 代码级拦截。
如果大模型仍然返回 workflow.list，该调用不会真正访问数据库，系统会记录拦截日志，
并把受控观察结果返回给大模型，让它继续选择电商 MCP 或飞书 CLI。

因此外层 Agent 会直接判断：

    电商业务数据 -> ecommerce.list_tools / ecommerce.call_tool
    飞书办公操作 -> cli.run_skill
    普通问答 -> final_answer

只有以下情况才允许外层 Agent 使用 workflow.list：

1. Java 路由预检查没有完成或发生异常。
2. 后续明确增加“查看可用工作流”的用户意图。
3. 业务改造为允许二次动态检索工作流。

## 9. 关键日志

规则召回：

    [工作流路由] 工作流定义：workflowCode=...，
    workflowName=...，intentKeywords=...，
    description=...，规则分数=...，命中原因=...

候选结果：

    [工作流路由] 规则召回完成：候选数量=...，候选=[...]

命中执行：

    [工作流路由] 命中工作流：workflowCode=...，
    workflowName=...，置信度=...，原因=...

未命中：

    [工作流路由] 未命中工作流：原因=...
